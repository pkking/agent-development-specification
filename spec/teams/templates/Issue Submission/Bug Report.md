# Bug Report — 缺陷修复

> 在 backlog 仓 New Issue 时选本模板。标题用 `[缺陷]` 前缀（流程 1 走 user-view 模式，只回评一段「用户视角描述」，不写需求分析说明书 PR）。

## 标题格式

`[缺陷][<服务名>] <一句话现象描述>`

例：

- `[缺陷][数据中台] 贡献者详情页 502，复现率 100%`
- `[缺陷][机器人] /retest 命令偶现无响应（约 5%）`

## 正文模板

```markdown
## 现象

<谁、什么环境（生产 / beta / 预览）、什么操作、看到什么结果（截图 / 日志最佳）>

## 期望

<正确的结果应该是什么样>

## 复现步骤

1. <第 1 步>
2. <第 2 步>
3. <...>

## 复现率与影响范围

- 复现率：<100% / 偶现：约 X% / 仅特定账号>
- 影响范围：<哪些社区 / 哪些用户 / 哪些版本>
- 严重程度：<P0 阻塞 / P1 严重 / P2 一般 / P3 体验>

## 已尝试

<已查过的日志、已 try 的解法、已排除的可能性>

## 相关参考

<关联的 issue / PR / 监控告警 / 截图 / 日志片段>
```

## 必含字段说明

| 字段             | 必填 | 说明                                                              |
| ---------------- | ---- | ----------------------------------------------------------------- |
| 现象             | ✓    | 必须可观察；模糊描述（「有时候不工作」）会被打回                  |
| 期望             | ✓    | 显式写「应该 X 而不是 Y」，便于 AI 判定验收标准                   |
| 复现步骤         | ✓    | 不可复现的 bug 需先复现再提 issue（除非生产事故，单独走复盘流程） |
| 复现率与影响范围 | ✓    | 影响 P0 直接评 `/accepts` 走快速通道                              |
| 已尝试           | 可选 | 帮 AI 流程 1 跳过已排除路径                                       |
